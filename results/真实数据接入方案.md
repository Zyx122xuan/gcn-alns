> 本文档是**可执行的施工方案**，不是调研综述。每一步都给出改哪个文件、改成什么、如何验证。

## 0. 结论先行

**好消息：代码已经是"数据源无关"的，真实数据接入的主要工作量不在改算法，而在拿数据 + 补两处保真度缺口。**

具体来说，三件事需要区分清楚：

| | 状态 | 工作量 |
|---|---|---|
| **解析器** | ✅ **已存在且已对齐接口**。`pegasus_parser.parse()` 与 `alibaba_parser.snapshot()` 输出的 dict 形状与 `synthetic.generate_raw_workflow()` / `generate_raw_machines()` **完全一致** | 0（已完成） |
| **接线** | ❌ 缺。`instance_builder.main()` 里**硬编码**调用 `synthetic.*`，没有任何 CLI 开关能切到解析器 | ~1 小时 |
| **数据** | ❌ 缺。仓库内无任何真实 trace 文件 | 下载为主，Alibaba trace 数十 GB 量级 |
| **保真度** | ⚠️ **两处真实信号被解析器读进来又丢掉了**（详见 §2），这是本方案里**学术价值最高的部分** | ~半天 |

所以路线是：**先花 1 小时把接线做通跑一个 end-to-end 冒烟测试，再决定要不要投入下载 Alibaba 全量 trace。** 不要反过来先下载几十 GB。

## 1. 为什么值得做：它能直接救活当前最弱的一条结果

这不是"为了政治正确加一句用了真实数据"。当前实验里有**一条明确站不住的结论**，而它的根因恰好是合成数据的一个具体缺陷：

**Fault-Domain（故障域隔离）消融在经验上是中性的。** 见 `REPORT.md` §7 与 `results/logs/domain_fault_exp*.txt`：

- 默认配置下 `w/o Fault-Domain` 的可行率 0.500 vs Full 0.493，**方向还是反的**（Holm p=1.000）；
- 补做了"整域下线"故障 + 粗粒度域（`coarse_k=2`）后，强制让 23% 的主动副本同域（隔离率从 100% 掉到 77%），结果**两者在域故障下的可行率仍然完全打平：33.3% vs 33.3%**。

我们当时把原因归给"动态重调度太强，已覆盖该失效模式"。这个解释是对的，但**只是一半**。另一半在 `layering.py:93`：

```python
fd = f"{layer}-{_hash_mod(m['machine_id'], groups[layer])}"
```

故障域是**用机器 ID 的 md5 哈希凭空造出来的**，`groups = {cloud: 8, edge: 12, device: 20}`。在 small 规模（50 节点）下这意味着 50 个节点被撒进 40 个域，**平均每域 1.25 个节点**。也就是说：

> 合成数据里"故障域隔离"这个约束**几乎是空约束**——随便放都天然隔离了，约束不约束没区别。测不出效果不奇怪，是数据本身没给它发挥空间。

而 **Alibaba trace 的 `machine_meta.csv` 里带有两级真实故障域字段 `failure_domain_1` / `failure_domain_2`**（机架 / 供电域级别），是真实的、有相关性的、粒度粗得多的分组。接上它之后：

- 如果 Fault-Domain 依然中性 → 这个结论就**真正可信了**，可以在论文里作为"形式化正确性保证但经验冗余"坦诚陈述，审稿人无法用"你的故障域是假的"反驳；
- 如果 Fault-Domain 显出效果 → **直接多一条实打实的贡献点**，且是当前论文里唯一一个"有机制、无证据"的组件。

**两种结果都比现在好。** 这是我建议优先做这一项的唯一理由，也是整个真实数据工作里投入产出比最高的一块。

## 2. 两处保真度缺口（本方案的技术核心）

解析器已经写了，但它们在两个地方把**最有价值的真实信号读进来又扔掉了**。

### 缺口 A：Alibaba 真实故障域被丢弃 ★ 最高优先级

`alibaba_parser.py:19` 的列定义里**明确包含** `failure_domain_1`、`failure_domain_2`：

```python
META_COLS = ["machine_id", "time_stamp", "failure_domain_1", "failure_domain_2",
             "cpu_num", "mem_size", "status"]
```

但 `snapshot()` 返回的 dict（`:51-59`）里**没有这两个字段**，于是 `build_nodes()` 只能回退去用 md5 哈希编造故障域。

**改法**：让 `snapshot()` 把真实域透出，并让 `build_nodes()` 优先采用。

`alibaba_parser.py` 的返回 dict 增加两个键：

```python
machines.append({
    "machine_id": str(mid),
    # ... 原有字段不变 ...
    "failure_domain_1": str(row["failure_domain_1"]),
    "failure_domain_2": str(row["failure_domain_2"]),
})
```

`layering.py` 的 `fd` 计算改为"有真实域就用真实域，否则回退哈希"（保持合成数据路径完全不变，向后兼容）：

```python
real_fd = m.get("failure_domain_1")
if real_fd:
    fd = f"{layer}-{real_fd}"          # 真实机架/供电域
else:
    fd = f"{layer}-{_hash_mod(m['machine_id'], groups[layer])}"   # 原合成回退
```

> 注意这里**仍然带上 `layer` 前缀**。因为我们的 layer 是按能力分位数重排出来的虚拟分层，同一真实机架里的机器可能被分到 cloud/edge 不同层；不带前缀会让"同域"跨层，与链路/成本模型不自洽。保留前缀的代价是域粒度被层切细，需要在冒烟测试里**实测每域节点数**（见 §5 验收项 V3）。

### 缺口 B：真实故障率可从 trace 推导，但没做

`layering.py:89` 已经预留了passthrough：

```python
if m.get("failure_rate") is not None:
    lam = float(m["failure_rate"])
else:
    lam = base_lambda * (1.0 + g1 * load + g2 * var)   # 当前走的是这条
```

即**代码已经准备好接收真实故障率，只是解析器不给**。当前所有节点的 λ 都来自配置里的 `base_failure_rate`（cloud 1e-6 等）+ 负载修正，是纯假设值。

Alibaba `machine_meta.csv` 有 `status` 列，且**每台机器有多条时间戳记录**——机器状态发生变化（如从 `on` 变为 `off`/`unavail`）就是一次真实的下线事件。由此可估计每台机器的经验故障率：

```
λ_k ≈ (该机器在观测窗内的状态异常次数) / (观测窗时长)
```

**建议做法（务实版）**：不要追求单机精确 λ（单机事件数太少，估计方差极大），而是**按真实故障域/机架聚合**成 λ，再赋给该域内所有机器。这样既用上了真实失效信息，又避免单机小样本噪声。同时把推导出的 λ 量级与配置里的 1e-6 做对比并在论文里报告——**如果真实量级差几个数量级，那本身就是一个值得写的发现**（意味着当前所有实验的故障强度设定偏离现实）。

⚠️ **风险提示**：v2018 trace 的 `status` 字段语义与采样完整性需要实际下载后核对；如果异常事件太稀疏（很可能，8 天窗口内 4000 台机器的硬件故障是低频事件），则**放弃缺口 B，只做缺口 A**，并在论文里明确写"故障率沿用文献典型值，敏感性分析见 §8"。不要为了"真实"去硬凑一个统计上不可靠的 λ。

### 缺口 C：WfCommons 的任务资源需求被丢弃（次要）

`instance_builder.py:40-41`：

```python
resource=float(job.get("cpu", 1.0)),
mem=float(job.get("mem", 1.0)),
```

而 `pegasus_parser.parse()` 的 `jobs[idx]` 只写了 `{"runtime": ...}`，没有 `cpu`/`mem`。→ **真实工作流的所有任务都退化成"1 核 1 单位内存"的同质任务**，节点的 `cpu_cap`/`mem_cap` 约束基本不起作用。

WfFormat 的 task 对象通常带 `cores`（或 `avgCPU`）与 `memoryInBytes`。**改法**：在 `pegasus_parser` 里补两行提取，缺失时回退 1.0：

```python
jobs[idx] = {
    "runtime": _job_runtime(job),
    "cpu": float(job.get("cores") or job.get("avgCPU") or 1.0),
    "mem": float(job.get("memoryInBytes", 0) or 0) / (1024**3) or 1.0,   # -> GiB
}
```

优先级低于 A/B，但改动极小、几乎零风险，建议一并做掉。

## 3. 数据获取清单

### 3.1 工作流：WfCommons

WfCommons 提供两类东西，**要两类都拿，用途不同**：

| 类型 | 是什么 | 在本项目中的用途 |
|---|---|---|
| **WfInstances** | 真实执行日志转成的 WfFormat JSON（含真实 runtime / 文件大小） | **真实性论证**。任务数固定、不可控，用作"真实实例验证集" |
| **WfChef / WfGen recipes** | 从真实实例学出的**生成器**，可合成任意规模但保持真实结构统计 | **规模对齐**。生成 50/150/500 任务的实例，接上主实验口径 |

- 来源：WfCommons 官方 GitHub 组织（`wfcommons`）下的 instances 仓库与 Python 包；具体仓库名/版本以官方 README 为准。
- 覆盖的工作流类型：Montage、CyberShake、Epigenomics、SIPHT 等——**与 `config/default.yaml:172` 的 `workflow_types: [Montage, CyberShake, Epigenomics, LIGO, SIPHT]` 高度重合**，说明当前合成数据的命名本来就是照着这套来的，替换后同名可比。
- 体积：JSON 级别，MB 量级，**无下载压力**。
- 许可：开源，学术引用即可（论文里需引 WfCommons 的方法学论文）。

> **LIGO 需单独确认**：若官方 instances 里没有 LIGO 对应集合，则真实数据实验的工作流集合改为 4 类，并在论文中说明；不要用合成 LIGO 混进"真实"结果里。

### 3.2 资源：Alibaba cluster-trace-v2018

- 来源：`alibaba/clusterdata` 官方仓库，选 **v2018** 版本（`alibaba_parser.py` 的列布局就是按 v2018 写的，换版本需改列定义）。
- 需要两个文件：
  - `machine_meta.csv` —— **小文件**，含容量、`status` 与两级 `failure_domain`。**这是缺口 A/B 唯一必需的文件。**
  - `machine_usage.csv` —— **大文件，数十 GB 量级**，含 CPU/内存利用率时间序列，用于 `cpu_util`/`mem_util`/`cpu_var`/`mem_var`。
- 关键判断：**`machine_meta.csv` 单独就能支撑最高价值的缺口 A。** `machine_usage.csv` 只影响负载与方差（当前合成值本来就是按 `load_levels` 区间均匀采的，与真实分布差异属"分布形状"级别，不是"真假"级别）。
- 因此**分两阶段下载**：先只拿 `machine_meta.csv` 做通全链路和缺口 A，验证有价值后再决定是否拉 usage 全量。`alibaba_parser.snapshot()` 已经用 `chunksize=1_000_000` 分块读，内存上是安全的，但磁盘和耗时要预留。

## 4. 接线改造（`instance_builder.py`）

这是唯一需要动主流程的地方。目标：**加开关，不改默认行为**——所有既有实验命令行为完全不变。

给 `main()` 增加三个参数：

```python
parser.add_argument("--wf-source", default="synthetic",
                    choices=["synthetic", "wfcommons"])
parser.add_argument("--wf-dir", default=None,
                    help="WfCommons/Pegasus JSON 目录（--wf-source=wfcommons 时必填）")
parser.add_argument("--res-source", default="synthetic",
                    choices=["synthetic", "alibaba"])
parser.add_argument("--alibaba-meta", default=None)
parser.add_argument("--alibaba-usage", default=None,
                    help="留空则只用 meta，util/var 回退为合成采样")
```

然后把生成循环里那两行硬编码换成分派。核心只有这么点：

```python
if args.wf_source == "wfcommons":
    raw_wf = pegasus_parser.parse(wf_json_path, name=wf_type)
else:
    raw_wf = synthetic.generate_raw_workflow(wf_type, n_tasks, seed)

if args.res_source == "alibaba":
    machines = alibaba_parser.snapshot(args.alibaba_meta, args.alibaba_usage,
                                       n_nodes=n_nodes, seed=seed + 10_000)
else:
    machines = synthetic.generate_raw_machines(n_nodes, load_level, seed + 10_000)
```

**三点实现注意：**

1. **`iid` 必须带数据源标记**，否则真实实例会和合成实例撞名、污染 resume 去重（runner 按 `(tag, algorithm, iid, rep)` 去重）。建议 `iid = f"{wf_type}_{scale}_{load}_{scenario}_r{rep}_real"`，并在 `meta` 里加 `"data_source": "wfcommons+alibaba"`。
2. **`--alibaba-usage` 允许留空**，此时 `snapshot()` 内部已有回退逻辑（`:49-50` 在无 usage 数据时用 `rng.uniform(0.2,0.6)`）——这正好支撑 §3.2 的两阶段策略，**只有 meta 也能跑通**。
3. **实例集独立成目录**，如 `data/instances/real_small/`，绝不与 `data/instances/` 混放。

## 5. 规模对齐与实例集设计

真实工作流的任务数是给定的，而主实验口径是 small=50 / medium=150 / large=500（`config/default.yaml:164`）。**不要去截断或补齐真实 DAG**——那会破坏结构统计，是最容易被审稿人抓的做法。

推荐**两层实例集**，各司其职：

**第一层：`real_*`（WfChef recipes 生成，规模严格对齐）**
用 recipes 按 50/150/500 生成，工作流类型 × 场景 × 重复数完全套用主实验口径。**这一层用于与现有合成结果做严格的同规模对照**，回答"换成真实结构统计后结论是否改变"。

**第二层：`realinst_*`（真实 WfInstances 原样使用，规模落在原始值）**
不做任何规模干预，按实际任务数分入 small/medium/large 桶（如 ≤80 → small，80~300 → medium，>300 → large）。**这一层用于"真实性"本身的论证**，在论文里作为附录证据，不参与主表对比。

两层都跑的成本很低（工作流侧数据量小），但话术上非常有用：主表用第一层保证可比，附录用第二层挡"你那还是合成的"这一质疑。

## 6. 实施步骤与验收点

严格按顺序，每步都有**硬验收标准**，不通过不进下一步。

### Step 1（~1 小时）：接线 + 纯合成回归
做 §4 的 CLI 改造，**先不碰任何真实数据**。

- **V1**：用默认参数（`--wf-source synthetic --res-source synthetic`）生成一批实例，与改造前生成的实例**逐字节 diff 应完全一致**。这是保证"不破坏已有 31/31 一致的实验结果"的唯一防线。

### Step 2（~半天）：只用 `machine_meta.csv` 打通真实资源侧
下载 Alibaba `machine_meta.csv`（小文件），做缺口 A（真实故障域）。usage 留空走回退。

- **V2**：`python -m gcnalns.data.instance_builder --res-source alibaba --alibaba-meta ... --scale small` 能产出合法实例，且 `load_instance()` 能读回、`compute_structural()` 不报错。
- **V3（关键）**：统计生成实例的**每故障域平均节点数**。合成基线是 ~1.25（见 §1）。**若真实域下该数值没有显著上升（比如仍 <2），说明 `layer` 前缀把域切得太碎，需要考虑去掉前缀或改用 `failure_domain_2`**。这一项不达标，整个缺口 A 的价值就没了，必须在这里拦住。

### Step 3（~1 小时）：工作流侧接通
装 WfCommons Python 包，用 recipes 生成 50/150/500 三档；同时下载若干真实 WfInstances。做缺口 C。

- **V4**：解析出的 DAG 任务数、边数、关键路径长度落在合理范围；`files` 无大面积零值（`pegasus_parser` 有中位数填补逻辑 `:78-83`，但**若填补比例 >30% 要警惕**，说明文件大小字段大面积缺失，需回看 JSON schema 变体）。
- **V5**：任务 `cpu`/`mem` 不再是全 1.0（验证缺口 C 生效）。

### Step 4（~数小时机时）：小规模对照实验
**只跑 small + 只跑 GCN-ALNS / ALNS / 2 个代表性 baseline**，先看信号，不要一上来全量。

- **V6**：真实数据下的可行率量级与合成数据可比（若真实数据下**所有算法**都近 0 或都近 1，说明 SLA 标定 `α/β` 在真实 `T_ref` 下失配，需要重新标定场景参数——这是很可能发生的，`generate_sla` 是相对 `T_ref` 的，理论上自适应，但真实 DAG 的关键路径占比可能与合成差别很大）。

### Step 5：重做 Fault-Domain 专项实验
用 `tools/tools_domain_fault_exp.py`（已支持域故障与 `coarse_k`）在真实故障域上重跑，直接回答 §1 的问题。

- **V7**：产出 Full vs w/o Fault-Domain 在真实域 + 域级故障下的可行率对比，**无论结论方向如何都如实写入 REPORT**。

## 8. 明确不建议做的事

1. **不要用真实数据全量重跑主实验来"替换"现有结果。** 现有结果已经过 31/31 claims 审计、rep10 + Holm 校正，是一套自洽且可辩护的证据链。真实数据的正确定位是**稳健性验证（附录）**，而非主结果。全量重跑要数十小时机时，且一旦数字与现有表格不一致，你要重写整篇论文的所有数值论述。
2. **不要为了"真实"而硬凑缺口 B。** 若 trace 的故障事件过于稀疏，坦诚写"故障率取文献典型值 + 敏感性分析"远比硬造一个统计不可靠的 λ 安全。
3. **不要截断/填充真实 DAG 去凑 50/150/500。** 用 recipes 生成（第一层）+ 原样使用（第二层）的两层设计来解决，见 §5。
4. **不要把合成的 LIGO 混进真实结果集。** 若官方无对应实例，就诚实地用 4 类工作流。

## 9. 论文话术建议

接入完成后，数据一节可以这样写（**基于实际做到的程度，不要提前写**）：

> 工作流结构与任务运行时长取自 WfCommons 的真实执行实例及其 recipe 生成器，涵盖 Montage / CyberShake / Epigenomics / SIPHT 等科学工作流；计算资源快照取自 Alibaba cluster-trace-v2018，其中节点容量、负载与**两级故障域**均来自 trace 原始字段，故障域直接对应真实机架/供电域划分。节点故障率取自文献典型值并做敏感性分析。
